# Безопасность, мониторинг трафика и реагирование

Дата: 4 ноября 2026 года. Статус: **требования и границы реализации**. Код и локальные проверки подготовлены, развёртывание на VPS и эксплуатационная приёмка не выполнены; см. [отчёт](verification.md).
Связанное предложение: [архитектура](architecture-proposal.md).

Текущая бюджетная ревизия: [два узла до €50/месяц](budget-50-eur.md). Требования безопасности сохраняются; мониторинг размещается на B вместо прежнего третьего узла C.

## 1. Цель и границы наблюдения

Администратору нужны скорость, объём трафика, доступность, ошибки и признаки атаки. Для этого не требуется сохранять посещённые сайты, DNS-запросы, URL, содержимое пакетов, сообщения или видео пользователей.

В первой версии — агрегаты по серверу/интерфейсу и служебные события. Диагностика конкретного профиля по запросу показывает только случайный идентификатор устройства, состояние и счётчики; история таких счётчиков по каждому пользователю по умолчанию не собирается. Псевдонимизация не делает данные юридически анонимными. Идентификаторы устройств и счётчики не должны попадать в публичную панель.

Не включать постоянно tcpdump, NetFlow с адресами назначения, DPI/расшифровку TLS, DNS query logging и полные дампы пакетов. Ограниченный захват для конкретного инцидента требует отдельного решения о цели, сроке и доступе, а не включается незаметно.

## 2. Предлагаемый стек

| Компонент | Назначение | Размещение |
|---|---|---|
| Prometheus | Метрики состояния и сетевых счётчиков | Узел B, закрытая служебная сеть |
| Grafana | Панель и правила оповещений | Узел B, доступ администратора |
| Loki, single binary | Поиск по разрешённым системным журналам | Узел B |
| Grafana Alloy | Сбор и фильтрация метрик/логов; ограниченная очередь | На каждом узле |
| Контрольный VPN-профиль и внешняя проверка | Проверка подключения, DNS, маршрута и доступности сборщика | A проверяет B; для общего отказа нужна точка вне OVHcloud, ещё не выбрана |

Компоненты бесплатны как самостоятельно размещаемое ПО; CPU, RAM, диск и обслуживание не бесплатны. Начальный резерв на B: 2 vCPU, 2–4 ГБ RAM и 15–20 ГБ ограниченного диска для наблюдаемости, с подтверждением нагрузочным тестом. Резерв вычитается из ресурсов VPN на этом узле. В бюджет €50 отдельная VM мониторинга не включена: при нехватке сначала оптимизировать сбор/кардинальность и пересчитать ёмкость; платное расширение требует отдельного согласования.

Источники: [Prometheus](https://prometheus.io/docs/introduction/overview/), [Grafana Alloy](https://grafana.com/docs/alloy/latest/), [Grafana Alerting](https://grafana.com/docs/grafana/latest/alerting/).

Мониторинг не участвует в пересылке пользовательских пакетов и не используется VPN как обязательный DNS/контроллер. При отказе B VPN на A продолжает работать; центральная панель недоступна, локальные журналы ограничены по размеру. Независимая проверка нужна, чтобы общий отказ OVHcloud или панели не означал молчаливую потерю наблюдения. Круглосуточная внешняя проверка, местоположение и канал уведомлений ещё не выбраны; платный внешний мониторинг не заказан. Взаимная проверка A/B не заменяет точку вне провайдера.

## 3. Защита панели и сборщиков

- Панель не публиковать в интернете; локальный/служебный listener, отдельный административный доступ.
- MFA для доступа администратора. Предварительный вариант без публичного IdP: SSH-ключ плюс TOTP при открытии административного туннеля, отдельная учётная запись Grafana, локальный доступ к панели через этот туннель. Альтернатива — аппаратный ключ с проверкой пользователя; recovery-процедура должна быть испытана.
- Пользовательский VPN не даёт доступа к SSH, Grafana, Prometheus, Loki, экспортерам и метаданным облака. Между клиентами пересылка запрещена.
- Межсерверная телеметрия идёт через отдельную служебную сеть; коллектор принимает только нужных агентов. Для удалённой загрузки журналов — аутентифицирующий прокси с mTLS, без публичного listener и без анонимного приёма.
- У Loki нет встроенного слоя аутентификации; включение multi-tenancy само по себе его не заменяет. Не считать закрытый порт единственной защитой. [Документация Loki](https://grafana.com/docs/loki/latest/operations/authentication/)
- Разделить права чтения журналов и изменения настроек. Отключить анонимный доступ и публичную регистрацию панели.
- Образы/пакеты закреплять на проверенных версиях; секреты не хранить в Compose, Git, dashboard JSON, URL и labels метрик. Контейнеры без Docker socket, без privileged, с минимальными capabilities; сборщик получает только нужные права чтения.
- Стек наблюдаемости ограничить по CPU/RAM/диску, чтобы всплеск логов не лишал пользователей VPN.

## 4. Что показывать на панели

| Раздел | Данные |
|---|---|
| Состояние | Доступность каждого узла, результат контрольного туннеля, версия конфигурации |
| Трафик | Входящие/исходящие Мбит/с, пакеты/с, дневные и месячные байты, прогноз месячной квоты |
| Качество | RTT, jitter, loss до контрольных целей; данные пользовательских сетей при наличии измерений |
| Ресурсы | CPU, steal, RAM, OOM, файловая система, заполнение conntrack, сетевые ошибки/drop |
| VPN | Число настроенных устройств, результат синтетического handshake, сбои сервиса; количество недавно передававших данные peers как приблизительный индикатор |
| Безопасность | Ошибки/успехи административной аутентификации, изменения конфигурации, неожиданные сервисы, обновления безопасности |
| Эксплуатация | Последний успешный backup, результат восстановления, возраст синхронизации отзывов, доступность доставки оповещений |

WireGuard не имеет понятия активной пользовательской сессии как веб-приложение: старый handshake спящего телефона не является доказательством поломки. Отслеживать контрольный активный профиль, а не тревожить по каждому неактивному устройству. Счётчики должны корректно учитывать перезапуск сервиса и обнуление интерфейса; сверка фактического биллинга обязательна.

## 5. Политика журналирования и хранения

| Категория | Состав | Предлагаемое хранение |
|---|---|---|
| Журнал управления доступом | Время, случайный ID устройства, операция, версия конфигурации, результат на каждом узле, ID администратора | 30 дней |
| Системные/служебные ошибки | Код ошибки, компонент, версия, перезапуск/OOM, время | 7 дней |
| SSH и административная аутентификация | Успех/отказ, учётная запись администратора, исходный административный IP при необходимости расследования | 7 дней; доступ ограничен |
| Агрегированные метрики серверов | Скорость/байты/ресурсы/контрольная доступность, без адресов сайтов и клиентских labels | 30 дней |
| Разрешённые материалы расследования | Минимум относящихся к инциденту записей, причина сохранения и владелец | Отдельный ограниченный архив, срок определяется для инцидента |

Фильтрация выполняется до отправки: предпочтителен allowlist полей/сервисов. Маскирование регулярным выражением — дополнительная защита. Не собирать полный вывод `wg showconf`, экспорт профилей, QR, environment, заголовки авторизации и аргументы команд с секретами. Для аудита файлов фиксировать изменение и исполнителя, не содержимое ключевых файлов; не включать без разбора аудит всех `execve` и оболочки.

Локальный journal: ротация, размер и срок ограничены. Очередь Alloy также ограничена; при превышении выводится событие потери телеметрии. У Loki явно включить retention/compactor и проверить фактическое удаление: по умолчанию удаление по сроку не включено. Политика должна распространяться на локальные буферы, резервные копии, snapshots и экспортированные инциденты, а не только интерфейс Grafana. [Retention Loki](https://grafana.com/docs/loki/latest/operations/storage/retention/)

## 6. Начальные правила тревог

Пороги ниже — стартовые настройки, корректируются по пилоту; это не доказательство взлома или гарантированное время реагирования человека.

| Событие | Условие | План реакции |
|---|---|---|
| Узел недоступен | 3 неудачные проверки с интервалом 20 с | Критическая тревога, инструкция резервного профиля, проверить провайдера |
| VPN не работает при доступном хосте | Контрольный туннель/маршрут не проходит ≥60 с | Проверить VPN, DNS, firewall и релиз; не перезапускать все узлы одновременно |
| Перегрузка | CPU >85% 5 минут, loss >1% 5 минут либо устойчивый рост RTT | Сопоставить с трафиком, CPU steal и PPS; перераспределить нагрузку |
| Вероятный DDoS | PPS/новые соединения резко выше обученного базового уровня вместе с drop/перегрузкой либо событие mitigation провайдера | Проверить upstream mitigation, включить согласованные ограничения, обратиться к провайдеру при необходимости |
| Административная атака | ≥10 неудачных входов за 5 минут; успешный вход с неожиданного источника | Проверить попытку, временно ограничить административный источник; не блокировать весь пользовательский диапазон |
| Изменение защиты | Несогласованное изменение SSH/firewall/unit-файлов или внезапный новый listener | Сохранить минимальные доказательства, изолировать узел, проверить остальные |
| Риск стоимости | 70/85/95% квоты либо прогноз превышения бюджета | Предупредить администратора, проверить фактический счётчик, согласовать перераспределение |
| Сбой хранения | Диск <20% свободен или log volume достиг 80% лимита | Ротация по политике; сохранение работоспособности VPN приоритетнее бесконечного хранения |
| Сбой восстановления | Нет успешной копии >26 часов или тест восстановления не выполнен в установленный период | Исправить копии, проверить независимое хранение |
| Сбой наблюдаемости | Внешняя проверка не видит heartbeat сборщика | Отдельная тревога, локальная проверка A/B |

Тревоги дедуплицировать, применять задержку и ограничение частоты. Получатель — администратор; выбраны оба канала — личный Telegram и email. Подготовка обоих реализована, но реальные получатели, учётные данные и доставка ещё не настроены/не проверены; сообщения и тестовые уведомления сейчас никому не отправлялись. В уведомлениях — узел, симптом, время, ссылка на закрытую панель; без ключей, IP пользователей и сайтов.

Для серверного обнаружения использовать метаданные и счётчики, без анализа содержимого трафика. Внешний SIEM/Wazuh и тяжёлый IDS не включать автоматически: для двух узлов сначала достаточно закрытых журналов, событий изменения и проверок. Расширять при выявленном пробеле, с оценкой ресурсов и конфиденциальности.

## 7. DDoS и firewall

Крупную атаку нужно фильтровать до узкого внешнего канала. OVHcloud описывает Anti-DDoS; эффективность для выбранного протокола/IP и влияние mitigation на легитимный UDP проверяются в пилоте и по условиям сервиса. Это не обещание неуязвимости. [Защита OVHcloud](https://www.ovhcloud.com/en/security/anti-ddos/)

Локально: default-deny входящего трафика, необходимые порты VPN и защищённого администрирования, фильтрация поддельных источников в соответствии с маршрутизацией, запрет открытого DNS-рекурсора и пользовательского доступа к служебным подсетям. Сохранить нужный ICMP/ICMPv6 для PMTU/NDP, не ломать MTU тотальным запретом ICMP.

Не делать автоматическую глобальную блокировку пользователей по одному всплеску: многие находятся за общим CGNAT. Не применять общий небольшой UDP rate limit ко всем VPN-пакетам: он уничтожит пропускную способность. Ограничения административных запросов и служебных ответов настраиваются отдельно от пересылаемого видео. Пересылку событий firewall не превращать в запись всех IP назначения пользователей.

Не проводить DDoS-атаку для проверки. Допустимы согласованные нагрузочные испытания между своими узлами, проверка событий и условий защиты провайдера.

## 8. Основные угрозы и ответ

| Угроза | Профилактика | Реагирование |
|---|---|---|
| Украдено устройство/профиль | Отдельные ключи, блокировка экрана, отсутствие общего профиля | Отозвать на всех узлах, выдать новый; проверить подтверждения отзыва |
| Root-компрометация узла | Минимум сервисов, обновления, закрытое управление, независимые копии | Изолировать через провайдера, не доверять локальным логам, пересоздать из проверенного образа, заменить серверные и затронутые ключи |
| Компрометация администратора | MFA, отдельные ключи/учётки, зашифрованный реестр, проверка изменений | Заблокировать административные полномочия, сменить секреты управления и оценить все узлы |
| Ошибка firewall/маршрутов | Проверка конфигурации, поочерёдное применение, консоль и rollback | Откатить один узел, не распространять сбой на остальные |
| Злоупотребление пользователем | Изоляция, запрет публичных входящих сервисов/рекурсора, правила пользования | Ограничить/отозвать профиль без записи истории всех пользователей |
| DDoS/ошибка маршрута | Провайдерская защита и независимые узлы | Сопоставить внешние проверки, переключить пользователей, работать с провайдером |
| Утечка через панель/логи | Закрытый доступ, allowlist полей, ограниченная выдача прав | Ограничить доступ, определить объём утечки, отозвать затронутые секреты, удалить лишние копии по правилам |
| Потерян сборщик | Локальные ограниченные логи, внешняя проверка | Восстановить сборщик независимо от VPN, учесть пропуск телеметрии |

VPN защищает участок между устройством и узлом, но не делает сайты доверенными, не заменяет HTTPS и не скрывает всё от скомпрометированного сервера или хостинг-провайдера. Резервные копии конфигурации шифруются до передачи; ключ расшифрования хранится отдельно. Серверные snapshots могут содержать рабочие секреты и требуют отдельной политики хранения/доступа.

## 9. Проверки перед эксплуатацией

- Из внешней сети доступен только разрешённый набор портов; пользовательский профиль не открывает административные endpoints.
- MFA обязательна на реальном пути к панели; проверены потеря второго фактора и аварийное восстановление.
- Ввести специальную несекретную тестовую метку в запрещённые поля и убедиться, что они не доходят до Loki/экспортов. Настоящие секреты для тестирования не использовать.
- Проверить каждый тип тревоги безопасным управляемым событием; получить подтверждённую доставку после выбора канала.
- Проверить ротацию, удаление по сроку и поведение при заполнении/отключении диска/сборщика.
- Отключить мониторинг и доказать, что остальные VPN-узлы продолжают работать.
- Проверить утечки, отзыв, восстановление, права backup и нагрузку мониторинга по критериям основного предложения.
- Проверить уязвимости зависимостей/образов и доступные security updates перед установкой; не заявлять выполненный аудит без результатов.

В репозитории реализованы конфигурации стека, подготовка обоих каналов уведомлений, SSH/MFA guard, firewall, ограниченные журналы и локальные проверки. Полный набор из четырёх образов и двух подписанных плагинов прошёл HIGH/CRITICAL-проверку 4 ноября 2026; первоначальный уязвимый комплект Grafana заменён. Реальные запросы через панель, исчезновение/восстановление одного узла и предупреждение о сертификате проверены в изолированном стенде. Теперь 11 правил: добавлены истечение сертификатов и рассогласование ревизий; выражения сохраняют метку узла, а пропавший ряд метрик не скрывает отказ. Настройка MFA на реальных VPS, фактическая доставка оповещений и клиентские испытания ещё не выполнены; см. [отчёт](verification.md).

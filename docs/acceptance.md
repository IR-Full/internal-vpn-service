# План приёмки на реальной инфраструктуре

Локальные тесты и native-валидаторы перечислены отдельно в [отчёте](verification.md). Они не заменяют испытания на VPS, пользовательских ОС и маршрутах российских операторов.

## Безопасность и управление

Проверить внешним сканированием **своих** узлов: публичны только согласованные UDP VPN-порты и SSH для административного allowlist; нет публичного Grafana/Prometheus/Loki/DNS-рекурсора. Пользователь не достигает административных адресов/портов, соседнего клиента, служебной подсети и metadata. Проверить spoofing адреса своего peer.

Проверить создание 100 пользователей/300 устройств, отказ четвёртого активного устройства, индивидуальный отзыв и замену. Отозванный профиль не работает на обоих узлах, второй профиль сохраняет работу. Отключить один узел при отзыве и проверить процедуру карантина/синхронизации перед возвратом. Старую ревизию нельзя применить поверх новой.

В свежем SSH-соединении вход без TOTP не работает, неверный TOTP отклоняется, root/парольный вход запрещены. Проверить rollback firewall/SSH, включая пропуск времени подтверждения; timeout не должен считаться успешной настройкой.

## Клиенты и утечки

Для Windows, macOS, Linux, Android, iOS и выбранных телевизоров/роутеров вести отдельные протоколы с версиями ОС/клиента. Проверять IPv4, IPv6 и DNS при подключении, переподключении, аварии сервера, ручном переключении A/B, сне/пробуждении и Wi-Fi↔LTE.

Захват только на тестовом устройстве и контролируемых DNS/HTTP-целях: при полном туннеле снаружи видны только необходимые служебные пакеты и шифрованный обмен с узлом. В текущем IPv6-режиме внешнее IPv6-соединение либо блокируется в туннеле, либо приложение использует IPv4; прямой выход IPv6 запрещён. Системная защита после выключения VPN должна быть проверена, а не предполагаться по наличию `AllowedIPs`.

Проверить браузерный DoH/QUIC, фоновые приложения, несколько сетевых интерфейсов и конфликт с другими VPN. Если платформа не обеспечивает требуемую блокировку при обрыве, это фиксируется как ограничение; использовать совместимый клиент/роутер, не скрывать результат.

Исключения для выбранных российских сервисов включать только после отдельных тестов всех доменов/CDN, DNS/IPv6 и параллельной работы других приложений. На неподдерживаемых платформах оставить полный туннель.

## Производительность

Сначала измерить канал без VPN к тому же собственному контрольному серверу. Затем тот же маршрут через VPN: upload/download, RTT, jitter, loss, CPU/RAM/steal и температуру/загрузку роутера. Встроенные speed test провайдеров и паспорт 2 Гбит/с не являются скоростью сервиса.

Для одного клиента подготовлен `tools/benchmark.py`, запускающий реальный iperf3 в обоих направлениях и сохраняющий JSON. Цель — свой разрешённый сервер за VPN, его порт открывается только для нужных тестовых источников. Не нагружать YouTube/чужие сервисы искусственными массовыми запросами.

```sh
python tools/benchmark.py --target IP_СВОЕГО_КОНТРОЛЬНОГО_СЕРВЕРА --seconds 60 --flows 4 --out .state/bench/client-baseline.json
```

Четыре потока одного peer не равны четырём пользователям. Для ступеней 25/50/75/100 нужны разные тестовые профили/туннели и достаточная суммарная ёмкость генераторов. Их можно размещать в изолированных пространствах имён/контейнерах на нескольких своих нагрузочных машинах; не оплачивать новые машины без согласования. Контрольные серверы iperf3 должны поддерживать нужную конкуренцию/набор портов. Проверить, что именно генератор/цель не является ограничением.

| Испытание | Предварительный критерий |
|---|---|
| Ёмкость каждого узла | ≥800 Мбит/с полезного смешанного трафика 60 минут, на B вместе с мониторингом |
| Продолжительный прогон | 24 часа переменной нагрузки без OOM, роста утечек памяти и постоянного переполнения conntrack |
| Рабочая загрузка | CPU в среднем <70%, RAM <75%; p95 роста RTT под нагрузкой относительно того же холостого VPN-пути ≤30 мс |
| Звонки | Loss <1%, jitter p95 <30 мс на выбранных контрольных путях |
| Смена сети | Переподключение к прежнему узлу ≤30 с на проверенном клиенте |
| Отказ узла | До 50 активных устройств на оставшемся, ручной выбор резерва ≤2 мин после обнаружения при готовом пользователе |
| Рабочие ступени | 30–70 устройств; отдельно 100 устройств как расширенная проверка |
| Стресс | 200/300 активных устройств и 4K: установить фактический предел, не обещать прохождение в €50 |

Результат записывать с временем, ОС/версией клиента, оператором, регионом, параметрами потоков и независимым baseline. Сравнение двух разных географических путей не изолирует накладные расходы VPN. Не выдавать Docker-стенд на одном компьютере за измерение VPS или российских маршрутов.

## Мониторинг и восстановление

Безопасно сымитировать: остановку своего VPN-сервиса, недоступность узла, недоступность сборщика, неверный административный вход, отсутствие свежей копии, нехватку выделенного пространства журналов. Проверить создание/снятие каждой тревоги, ограничение повторов и **доставку одновременно в Telegram и email**.

Проверить TLS ingestion: без клиентского сертификата или с чужим CA отказ, правильный агент пишет только по разрешённым API-путям. Ввести несекретную уникальную метку в недопустимое поле тестового сообщения и убедиться, что исходная строка не появляется в Loki. Проверить фактическое удаление по retention, локальные буферы, ограничения ресурсов и поведение VPN при остановке Loki/Alloy.

Восстановить конфигурацию из независимого зашифрованного backup на чистую временную ОС. Сверить текущие отзывы и права файлов. Копия самого провайдера отдельно от внешнего backup не освобождает от этого теста.

Проверку DDoS выполнять через условия/события защиты провайдера и разрешённые лабораторные события. Не инициировать настоящую DDoS-атаку.

## Допуск

После получения доказательств владелец заполняет приватный `.state/acceptance.yml`: `notifications_tested`, `restoration_tested`, `client_leak_tests_passed`, `provider_contract_verified`, `russia_legal_review_completed`, `monthly_total_eur`. Затем запускается `infra/verify.yml`. Это фиксирует ответственность за внешние результаты; флаги не являются заменой измерений и не должны заполняться автоматически «для зелёной галочки».

# Руководство администратора

## Перед заказом

Архитектура двух узлов согласована; разрешение покупать серверы пока не дано. При согласовании покупки можно провести выбор в видимом браузере владельца; вход, проверка личности и оплата выполняются владельцем. Ниже подготовлена последовательность для самостоятельной аренды.

1. Открыть [официальный раздел OVHcloud VPS](https://www.ovhcloud.com/en-ie/vps/). Для своих реальных страны и статуса проверить допустимость оформления договора и оплаты. Не заменять страну фиктивной. Описание европейской витрины не доказывает доступность услуги резиденту РФ.
2. Выбрать VPS-3, Ubuntu 24.04 x86_64, месячную оплату без длительного обязательства, один основной IPv4 и доступ к аварийной консоли. Проверить, что нужный образ ОС и оба физических дата-центра доступны.
3. Узел A и B — разные европейские площадки. Выбор Польши/Франции/Германии уточнить по пилоту и маршрутам. На старте американский узел не покупать.
4. Не включать Plesk/cPanel, Windows, балансировщик, дополнительные IP/диски. Проверить Anti-DDoS, условия трафика, продление и первоначальный платёж. Лимит на каждый сервер — €17/месяц с налогами и обязательными сборами; всё обслуживание вместе ≤€50.
5. Сначала один короткий пилот, затем второй сервер. До оплаты зафиксировать итоговую корзину и получить явное подтверждение владельца. Сейчас корзина и оформление на резидента РФ не проверены.

Ansible воспроизводит настройку уже приобретённых узлов. Платное создание VM не автоматизировано: здесь нет скрытых Terraform-ресурсов, API-токенов провайдеров и автоматически возникающих обязательств.

## Контроллер и секреты

Для Ansible нужен Linux/WSL-контроллер с Python 3.12–3.14 и OpenSSH; локальные проверки выполнены на Python 3.12. Это требование закреплённого `ansible-core==2.21.6`, см. [официальную матрицу поддержки](https://docs.ansible.com/projects/ansible/latest/reference_appendices/release_and_maintenance.html). Сам CLI поддерживает Python 3.11+, но полный набор из `requirements.lock` требует указанной версии контроллера. Установить зависимости из `requirements.lock`, затем `pip install --no-deps -e .`. Для локальной разработки на Windows предоставлен Docker-инструментарий; интерактивный SSH/MFA удобнее выполнять из Linux/WSL. Секреты хранить на зашифрованном диске и в каталоге с правами владельца. Linux chmod на Docker bind mount NTFS не заменяет проверку Windows ACL.

В Windows хранить рабочие данные в принадлежащем текущему пользователю каталоге NTFS внутри личной папки. Родительский каталог тоже должен быть закрыт для изменений другими пользователями.

На Linux:

```sh
umask 077
mkdir -p .state
chmod 700 .state
python3.12 -m venv .venv
. .venv/bin/activate
pip install -r requirements.lock
pip install --no-deps -e .
ssh-keygen -t ed25519 -f .state/admin_ed25519
```

Использовать пароль на SSH-ключе. Приватный SSH-ключ и passphrase реестра не передавать в чат. Файл `examples/fleet.json` содержит заведомо нерабочие адреса документации: скопировать в `.state/fleet.json` и заменить реальными адресами, своим публичным ключом и узким административным IPv4 CIDR. Интернет целиком в административный allowlist не включать.

```sh
vpnctl init --fleet .state/fleet.json
vpnctl add-user u001
vpnctl add-device u001 phone
vpnctl configure-alerting
```

Названия — случайные/условные идентификаторы, не обязательны ФИО/телефоны. Passphrase минимум 16 символов, желательно длинная случайная фраза. `configure-alerting` спрашивает оба канала: личный Telegram chat ID/token и email/SMTP. SMTP — порт 587, обязательный STARTTLS и проверка сертификата, предпочтителен отдельный app password. Команда только сохраняет настройки, не отправляет сообщения.

Получение Telegram bot token описано в [официальном руководстве Grafana](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/configure-telegram/). Настройку аккаунтов и бота можно провести вместе в интерфейсе по отдельному запросу; токен вводить только локально. Не передавать пользователям административный профиль или доступ к Grafana.

## Образы и подготовка inventory

```sh
python tools/lock_images.py
python tools/scan_images.py
vpnctl render --out .state/deploy
```

Сканер требует Docker CLI и работающий engine. Используются фиксированные digests образов и SHA256 архивов плагинов; проверяются все HIGH/CRITICAL, включая находки без исправления. Успешная проверка действует семь дней, требует отчётов всех шести артефактов, платформы linux/amd64 и совпадения состава. Ошибка сканера, отсутствие анализа бинарника, подмена состава и будущая дата закрывают допуск. На 4 ноября 2026 весь выбранный набор прошёл; повторить проверку перед установкой. Это не обещание отсутствия всех уязвимостей.

Grafana использует официальный slim-образ и только официальные подписанные Loki/Prometheus-плагины. `scan_images.py` скачивает точные архивы с проверкой SHA256, безопасно распаковывает их в `.state/grafana-plugins` и отдельно сканирует Go-бинарники через Trivy `rootfs`. Bootstrap повторно сверяет подготовленные файлы с архивами и копирует их в каталог версии на B; в контейнер он монтируется только для чтения. Проверка подписи остаётся включённой; автоматические установка/обновление и управление плагинами через панель отключены. При смене версии обновлять lock, сканировать и повторять `smoke_stack.py`; архивы плагинов не коммитить.

Результат: открытый inventory с адресами/публичными параметрами и **зашифрованный Ansible Vault** в `group_vars/all/vault.yml`. Для расшифрования Vault используется passphrase реестра, ввод через `--ask-vault-pass`. Серверные ключи, TLS-ключи, клиентские PSK, SMTP и Telegram остаются внутри Vault до доставки на соответствующий сервер. На работающем сервере нужные процессам ключи существуют в root/service-only файлах; абсолютное отсутствие секретов в оперативной памяти не обещается.

Для пилота AmneziaWG сначала `python tools/lock_amnezia.py` на Linux/в инструментальном контейнере. Он получает полный fingerprint официального PPA, checksum ключа и версии трёх пакетов Noble; установка затем проверяется APT с отдельным `signed-by`. Выбранный backend/совместимые параметры AmneziaWG задаются в fleet до init. Передать `.state/amnezia-lock.json` в Ansible через `-e @.state/amnezia-lock.json`. Не брать параметры от другого поколения протокола и не обещать поддержку текущего ядра до проверки DKMS на VPS. На существующей сети смена backend — отдельная миграция.

MTU по умолчанию 1380. При проблемах с большими пакетами измерить PMTU/потери и согласованно уменьшить `mtu` соответствующего узла в fleet (допускается 1280–1420), выполнить set-fleet/render/apply и переимпортировать клиентские профили. Не отключать ICMP ради «защиты» и не настраивать MTU по вымышленной скорости.

## Bootstrap и проверка

Перед применением с обновлённым кодом заново выполните `vpnctl render`. Ansible сверяет идентификаторы пары inventory и Vault. UDP-порт 51821 зарезервирован для служебного WireGuard. Если он указан у пользовательского узла в старом реестре, исправьте его через `vpnctl set-fleet` и экспортируйте профили заново.

Перед установкой обычных пакетов роль проверяет APT и `libapt-pkg6.0t64`: для Ubuntu 24.04 требуется версия не ниже `2.8.4ubuntu0.1` из-за [CVE-2026-109518](https://ubuntu.com/security/CVE-2026-109518). При необходимости выполняются native `apt-get` update и only-upgrade с `Acquire::Retries=0`; только после проверки версий допускается Ansible apt. Этот порядок нельзя обходить ручной установкой через старый APT. Для ручного восстановления использовать [официальную процедуру Canonical](https://ubuntu.com/blog/apt-vulnerability-fixes-available); ошибки репозитория или отсутствие исправления требуют устранения причины, а не отключения проверки подписей.

1. Через консоль провайдера проверить SSH host key. Добавить его в `known_hosts` по сверенным данным, не использовать `StrictHostKeyChecking=no`. Начальные пароль/ключ провайдера вводить локально.
2. Проверить исходный SSH-доступ и аварийную консоль. Перед сетевыми изменениями обеспечить себе достаточно времени для нового соединения.
3. Из корня проекта с указанием реального начального пользователя провайдера:

```sh
export ANSIBLE_CONFIG=infra/ansible.cfg
ansible-playbook -i .state/deploy/inventory.json infra/site.yml --syntax-check --ask-vault-pass
ansible-playbook -i .state/deploy/inventory.json infra/site.yml -u ubuntu --private-key .state/admin_ed25519 --ask-vault-pass --diff
```

Секретные задачи помечены `no_log`; не отключать его и не включать подробный отладочный лог Ansible. Если имя начального пользователя другое, заменить `ubuntu`; при начальном root — явно указать только для bootstrap. Проверка `--check` полезна, но на пустом хосте команды в ещё не созданных файлах могут быть недоступны; она не заменяет синтаксическую проверку и пилот.

4. Узлы устанавливаются последовательно. В конце каждого узла staging firewall включает таймер 120 секунд. Открыть **новое SSH-соединение** с разрешённого IP, проверить доступ, выполнить `sudo vpn-firewall confirm`, затем продолжить playbook. Если доступ не подтверждён, произойдёт откат к last-good/rescue; первый rescue сохраняет администрирование, но не пользовательский forwarding. Не подтверждать вслепую из старой сессии.
5. Проверить туннель, DNS и клиентский доступ. Пока не подтверждены MFA и остальные критерии, не выдавать доступ всему сообществу.

## Обязательная MFA администратора

На каждом сервере войти по новому ключу как `vpnadmin`, локально выполнить `google-authenticator` и сохранить секрет в `/home/vpnadmin/.google_authenticator` с правами 0600. Добавить TOTP в свой аутентификатор, recovery codes хранить отдельно. Не выводить QR/секрет в общие логи или чат. Проверить синхронизацию часов.

```sh
ansible-playbook -i .state/deploy/inventory.json infra/harden-ssh.yml -u vpnadmin --private-key .state/admin_ed25519 --ask-vault-pass
```

Guard планирует откат через 180 секунд, отключает root/парольный SSH, требует ключ + TOTP. В новом терминале проверить реальный вход с обоими факторами, явно запретив повторное использование старого соединения: `ssh -o ControlMaster=no -o ControlPath=none -i .state/admin_ed25519 vpnadmin@АДРЕС`. Затем выполнить `sudo vpn-ssh-guard confirm`. Оставлять аварийную консоль открытой до проверки. Для последующей автоматизации сначала открыть интерактивное SSH ControlMaster-соединение с MFA, используя `ControlPath=~/.ssh/vpn-service-%C` и `ControlPersist=15m`; Ansible использует уже аутентифицированное соединение, а не постоянный ключ, обходящий MFA.

## Панель и два канала уведомлений

```sh
ssh -i .state/admin_ed25519 -L 3000:127.0.0.1:3000 vpnadmin@АДРЕС_B
vpnctl grafana-password --out .state/grafana-password
```

После MFA открыть локально `http://127.0.0.1:3000`, пользователь `fleetadmin`, пароль взять из локального приватного файла и удалить экспорт после использования. Порт 3000 снаружи открывать не нужно.

В Grafana проверить две data sources, панель Private VPN, все правила и contact point `fleet-admin` с Telegram и email. Отправить тест **только своим подтверждённым адресатам**, убедиться в фактической доставке обоих сообщений и последующего resolved-сообщения. Настройка без такой проверки не считается рабочей доставкой. SMTP/TG учётные данные не встроены в Git или Docker environment; на сервере они нужны Grafana в служебных файлах.

## Независимые резервные копии и допуск к эксплуатации

Подготовить отдельное внешнее SFTP/S3/REST-хранилище, отличное от двух VPS/их аккаунта. Лимит копии — €4/месяц; при наличии собственного места можно не покупать новую подписку. SFTP host key сверить, ключ для backup отделить от административного, ограничить правами хранилища. Доступ/credentials API провайдеров здесь не создаются автоматически.

Создать `.state/backup.vault.yml` через `ansible-vault create`: `restic_repository` с адресом выбранного внешнего репозитория и случайный `restic_password` не короче 24 символов. Минимальный путь — SFTP с SSH-ключом на узле. Для S3/REST допускается зашифрованный словарь `restic_environment` с необходимыми `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN` либо `RESTIC_REST_USERNAME`/`RESTIC_REST_PASSWORD`; он переносится в root-only EnvironmentFile. Не путать разные пароли Vault и Restic.

```sh
ansible-playbook -i .state/deploy/inventory.json infra/backup.yml -e @.state/backup.vault.yml -u vpnadmin --ask-vault-pass
```

При первом использовании отдельно инициализировать новый Restic-репозиторий с тем же environment (`restic init`), затем на обоих узлах `sudo systemctl start vpn-backup.service`. Не выполнять `init` вместо выяснения ошибки доступа к существующему репозиторию. Проверить восстановление на чистую временную машину.

Пройти [приёмку](acceptance.md), записать фактические доказательства и только затем выполнить `infra/verify.yml` с приватным файлом приёмки. Флаги доставки/восстановления/утечек/договора/юридической проверки и сумма расходов не должны выставляться по предположению. Пока VPS, результаты и адресаты не предоставлены, этот этап остаётся невыполненным.

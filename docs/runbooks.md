# Эксплуатация и реагирование

## Добавление, отзыв и замена устройства

Все команды выполняются локально с passphrase, секреты в аргументах не указываются:

```sh
vpnctl add-user u002
vpnctl add-device u002 laptop
vpnctl render --out .state/deploy
ansible-playbook -i .state/deploy/inventory.json infra/peers.yml -u vpnadmin --ask-vault-pass
vpnctl export laptop --out .state/exports/laptop-first
```

Экспорт — два **открытых секретных** файла с правами владельца, предназначенные для импорта на устройство. Передать лично или по подходящему защищённому каналу, удалить временную выдачу после проверки. Не прикладывать к общим чатам/тикетам. Ключи шифруются в реестре и Vault, но клиенту для импорта нужны расшифрованные данные.

```sh
vpnctl revoke laptop
vpnctl render --out .state/deploy
ansible-playbook -i .state/deploy/inventory.json infra/peers.yml -u vpnadmin --ask-vault-pass
```

**Локальный revoke меняет желаемое состояние, а не мгновенно удалённые серверы.** Завершение отзыва — подтверждённая новая ревизия на A и B и отрицательный тест старого профиля. Playbook пытается обработать оба доступных узла; если один недоступен, отзыв остаётся частичным. Перед возвращением такого узла ограничить его через консоль провайдера, применить актуальную ревизию, проверить старый ключ и только затем открыть VPN.

Для замены отозвать старое устройство, создать новое ID и применить оба изменения. `delete-user` удаляет текущие записи и ключи пользователя из реестра, но изменение также нужно применить на оба узла. Журнал административной операции может храниться до 30 дней; старые зашифрованные копии — до окончания своей политики. Удаление файла не гарантирует стирание с SSD и из snapshots провайдера.

Для плановой замены ключей активного устройства без нового адреса есть `vpnctl rotate-device laptop`: затем render, peers.yml и новый экспорт. Старые ключи перестанут работать после применения на узлах. При компрометации ключей сервера — `vpnctl rotate-server vpn_a`, полный render/site.yml на обоих узлах и новая выдача профиля A всем затронутым устройствам; B остаётся отдельной рабочей точкой. `vpnctl renew-telemetry` перевыпускает CA и mTLS-сертификаты перед истечением срока; применять последовательно на обоих узлах, ожидать краткий разрыв телеметрии. После взлома B отдельно заменить пароли/токены Grafana, Telegram и SMTP; bootstrap-пароль Grafana из файла сам по себе не сбрасывает пароль уже существующей SQL-учётной записи.

## Резервирование и сбои

Если A недоступен, пользователь вручную выбирает профиль B. В уменьшенной архитектуре аварийная цель — до 50 одновременно активно передающих устройств. Во время перегрузки сначала предложить снизить качество видео и остановить тяжёлые загрузки; не включать DPI для распознавания сайтов. Два OVHcloud не защищают от общего отказа провайдера/аккаунта.

При отказе B панель Grafana и основная доставка тревог недоступны, A продолжает VPN. Локальные события остаются ограниченными. Для уведомления об отказе самого сборщика нужна отдельная проверка вне OVHcloud; она ещё не подключена. Проверка A→B помогает при одиночном сбое, но не заменяет внешний канал при общем отказе.

## Обновления и откат

1. Проверить доступ через консоль, актуальную копию и второй узел. Сначала обновлять один сервер.
2. Для контейнеров обновить выбранные версии в `tools/lock_images.py`, получить новые digests, выполнить `scan_images.py`, валидаторы и smoke-тест. Не использовать `latest` и не считать успешный pull аудитом.
3. Сохранить прежний прошедший аудит lock и зашифрованный реестр. Откат образов допустим только если прежний набор остаётся допустимым по безопасности.
4. `vpnctl render`, синтаксическая проверка, последовательный `site.yml`. При сетевых изменениях подтвердить свежий SSH-доступ в пределах таймера, при SSH/MFA — отдельный 180-секундный guard.
5. Проверить доступ, DNS, маршрут, тревоги и счётчики. Потом обновить второй узел. Автоматические обновления security-пакетов не перезагружают серверы; необходимость reboot проверить вручную и выполнить по одному.

Не откатывать реестр на старую ревизию для восстановления удалённого устройства. Runtime отклоняет старую или противоречивую ревизию. При миграции backend/подсети планировать отдельную замену интерфейса и выдачу профилей; `set-fleet` запрещает такую миграцию «на месте». Обновление адресов/порта/административного allowlist через `set-fleet --fleet .state/fleet.json` требует нового render/apply и при необходимости переиздания файлов с новым endpoint.

## Резервные копии и восстановление

```sh
vpnctl backup --out .state/backups/registry-YYYY-MM-DD.enc
```

Копию скопировать на независимый носитель; passphrase хранить отдельно. Команда проверяет расшифрование, но не проверяет потерю всего компьютера. Серверные конфигурации — через Restic, ежедневно; после копии выполняется `restic check`. Это проверка целостности репозитория, а не полноценный тест восстановления.

Восстановление:

1. Создать чистый разрешённый сервер, проверить SSH host key и обновления. При признаках взлома не восстанавливать ОС целиком из недоверенного snapshot.
2. Восстановить **последний достоверный** зашифрованный реестр на защищённом контроллере. Проверить актуальный список отзывов и ревизию по независимым данным; если достоверного списка нет — перевыпустить затронутые ключи, не открывать восстановленную старую конфигурацию всем пользователям.
3. При смене IP обновить fleet, render и применить актуальную конфигурацию. При компрометации серверного ключа заменить его и переиздать соответствующие клиентские профили; простой возврат прежнего ключа небезопасен.
4. Из Restic извлекать нужные настройки в отдельный временный каталог, проверить права и происхождение, затем применять проверенный код. Не копировать устаревший `applied.json` поверх более новой ревизии действующего узла.
5. Пройти тесты отзыва, MFA, DNS/IPv6, маршрута и обоих уведомлений. Только затем возвращать узел в обслуживание.

Хранение конфигурационных копий Restic: 7 ежедневных, 4 еженедельных, 3 месячных; они содержат эксплуатационные секреты, но не историю сайтов. Смена/удаление секретов в текущем реестре не удаляет их немедленно из копий. Сроки snapshot провайдера проверить отдельно.

## Подозрение на взлом

Сначала определить затронутый узел по независимым проверкам. Через консоль провайдера ограничить его сеть, сохранить минимальные относящиеся к событию доказательства, проверить второй узел и административный контроллер. Не доверять локальным логам как неизменяемому доказательству после root-компрометации.

Пересоздать затронутый узел из проверенного образа, заменить его VPN/TLS/административные ключи и затронутые токены/пароли. Если скомпрометирован контроллер, считать раскрытым содержимое открытого реестра и оценить всю инфраструктуру. Массовая ротация требует планового переиздания, не обещается одной командой без последствий для клиентов.

Оповещения содержат технический симптом и узел, без приватных ключей и посещённых сайтов. Ограничить доступ к материалам расследования и назначить отдельный срок хранения. Это не полноценный SOC с гарантированным временем реакции человека.

## DDoS или всплеск нагрузки

Сопоставить PPS, drop, CPU/steal и события upstream-защиты. Высокий трафик сам по себе не доказывает атаку: это может быть видео. Крупный flood должен фильтроваться до внешнего канала провайдером; firewall не расширяет перегруженный канал.

Не блокировать всех пользователей за общим CGNAT по одному адресу и не вводить маленький общий лимит UDP-пакетов. Для заявок провайдеру использовать время, IP своего узла и агрегированные метрики; не отправлять содержимое пользовательских пакетов. Обращения провайдеру не отправляются автоматически без разрешения владельца.

При нехватке диска раньше всего ограничивается наблюдаемость: Prometheus имеет лимит TSDB, Loki — retention/ingestion; сборщик останавливает Loki при свободном месте <10%. Найти причину, проверить доставку тревог, освободить место по политике и вручную запустить Loki после устранения. VPN не следует останавливать ради бесконечного накопления журналов.
